## Требования

### Управляющий компьютер (control node)

- Linux, macOS или Windows с WSL;
- Python 3, Ansible Core версии 2.18 или новее, Make, Git и SSH-клиент;
- SSH-ключ для подключения к серверу;
- пароль от Ansible Vault с секретами приложения;
- доступ в интернет для установки Ansible-зависимостей.

Перед запуском создайте локальный файл `inventory.ini` со своим публичным IP и
SSH-пользователем. Этот файл игнорируется Git:

```ini
[app]
app-server ansible_host=<публичный-IP> ansible_user=ubuntu ansible_port=22
```

### Целевой сервер

- виртуальная машина с Ubuntu 24.04 LTS, Python 3, `apt` и SSH;
- пользователь с правами `sudo` без запроса пароля;
- статический публичный IPv4-адрес и исходящий доступ в интернет;
- входящие TCP-порты `22`, `80` и `443`, разрешённые в облачной группе
  безопасности;
- A-записи `uit14.ru` и `www.uit14.ru`, направленные на публичный IP сервера.

Docker, Docker Compose, Git, cURL и UFW устанавливаются подготовительным
playbook. Nginx и Certbot устанавливаются во время деплоя.

## Развёртывание

Установите зафиксированные версии ролей и коллекций Ansible:

```bash
make install
```

Подготовьте новый сервер:

```bash
make prepare
```

Подготовительный playbook:

- устанавливает Docker, Docker Compose, Git, cURL и UFW;
- запускает Docker и включает его автоматический запуск вместе с системой;
- добавляет SSH-пользователя в группу `docker`;
- открывает входящие TCP-порты `22`, `80` и `443`;
- запрещает остальные входящие подключения и разрешает исходящие;
- включает firewall UFW.

Подготовку достаточно выполнить один раз для каждого нового сервера. Повторный
запуск безопасен: Ansible применит только отсутствующие изменения.

Разверните образ с тегом, указанным в `group_vars/app/vars.yml`:

```bash
make deploy
```

Чтобы развернуть новую версию, укажите полный SHA Git-коммита образа:

```bash
make deploy IMAGE_TAG=<full-commit-sha>
```

Чтобы откатиться к ранее развёрнутому образу, укажите SHA соответствующего
Git-коммита:

```bash
make rollback IMAGE_TAG=<previous-full-commit-sha>
```

Роль развёртывания не принимает изменяемые теги, например `latest`. Логи
приложения хранятся на сервере в `/srv/project-devops-deploy/logs`. Постоянные
данные находятся в Managed PostgreSQL, а загруженные файлы — в Object Storage,
поэтому они сохраняются при замене контейнера.

## Nginx и статические файлы

Во время деплоя Ansible устанавливает Nginx и формирует его конфигурацию из
Jinja2-шаблона. Nginx принимает HTTPS-запросы на порту `443`, а запросы на порт
`80` перенаправляет на HTTPS. Контейнер приложения доступен только локально на
`127.0.0.1:8080`.

Файлы сборки фронтенда по пути `/assets/` кешируются Nginx на семь дней. Клиенту
для них передаётся заголовок `Cache-Control` с длительным сроком хранения,
поскольку имена файлов содержат хеш содержимого. API и `index.html` в этот кеш
не попадают. Статус кеша возвращается в заголовке `X-Cache-Status`: первый
ответ содержит `MISS`, а повторный — `HIT`.

## HTTPS

Сертификат Let's Encrypt для `uit14.ru` и `www.uit14.ru` выдаётся автоматически
ролью `geerlingguy.certbot` во время первого деплоя. Для проверки домена
используется webroot, поэтому останавливать Nginx не требуется. Регистрация в
Let's Encrypt выполняется без адреса электронной почты.

Роль Certbot создаёт ежедневное задание cron для автоматического продления.
После успешного обновления сертификата deploy hook проверяет конфигурацию и
перезагружает Nginx. Разрешены только TLS 1.2 и TLS 1.3 с современными наборами
шифров, а HTTP-запросы перенаправляются на HTTPS.

## Managed PostgreSQL и миграции

Хост, порт, имя базы и режим SSL находятся в `group_vars/app/vars.yml`. JDBC URL
собирается из этих переменных автоматически. Пользователь и пароль базы данных
хранятся в зашифрованном `group_vars/app/vault.yml`.

Перед запуском приложения роль создаёт закрытый env-файл и запускает Flyway,
если изменились SQL-миграции, параметры подключения или образ приложения.
Успешно завершённый контейнер миграций используется для определения того, нужен
ли повторный запуск.

## Хранение изображений в Object Storage

Для приложения используется закрытый бакет Yandex Object Storage
`uit14-bulletins-images`. Бакет подготовлен вручную следующим образом:

1. В Object Storage создан бакет без публичного доступа.
2. Создан отдельный сервисный аккаунт `bulletins-s3`.
3. Сервисному аккаунту назначена роль `storage.uploader` только на этот бакет.
4. Для сервисного аккаунта создан статический ключ доступа.
5. Идентификатор и секретная часть ключа зашифрованы в Ansible Vault.

Публичные параметры подключения находятся в `group_vars/app/vars.yml`. В
зашифрованном `group_vars/app/vault.yml` находятся переменные
`vault_s3_access_key` и `vault_s3_secret_key`. Во время деплоя роль формирует
закрытый env-файл с именем бакета, регионом, endpoint и ключами доступа. Бакет
остаётся закрытым, а приложение создаёт временные подписанные ссылки для
скачивания файлов.
